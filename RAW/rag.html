Report Overview

This technical report outlines the end-to-end design, technology stack, and step-by-step data flows of the EduNest Entry Test Module. It details the offline FSc syllabus document ingestion pipeline, backend Flask semantic vector search, Groq Llama 3.3 batch question generation, dual-layered fallback safety loops, and React-side anti-cheat mock testing logic.

1System Architecture & RAG Flow

Traditional AI question generation systems rely on client-side prompt engineering, passing curriculum lists to an LLM. This model suffers from three critical vulnerabilities: (1) hallucinations where the model creates equations or facts outside the local Pakistani board syllabus, (2) security risk from exposing raw API authorization keys in client browsers, and (3) lack of compliance with official entry test marking structures (MDCAT/ECAT).

To resolve these challenges, EduNest leverages a secure Retrieval-Augmented Generation (RAG) architecture. In this design, the system behaves like an "open-book exam" coordinator. When generating mock tests, the server semantically queries local, verified FSc textbooks (Biology, Chemistry, Physics) stored as vectorized chunks, and forces the generative model to restrict its output context strictly to those textbook extracts.

Double-Phase Architecture

The architecture is split into two separate technical operations:

  • Phase A: Offline Ingestion Pipeline: Extracts text from official textbook PDFs, splits it into overlapping semantic blocks, embeds it into coordinate vectors, and stores it locally inside a ChromaDB database.
  • Phase B: Live Exam Generation API: Semantically queries the vector store when a student launches a mock test, structures context parameters, invokes Groq high-speed inference, and validates JSON questions.

2Offline Ingestion Pipeline (`ingest.py`)

The document ingestion script indexes official textbooks into coordinate vectors. This happens once, storing high-quality, extractable textbook content locally to support offline RAG operations.

1
Directory Structure Scanning
The system scans the python_backend/data/syllabus/ folders. Chunks are automatically mapped to metadata fields representing subject parameters, grades, and chapter names.
2
Text Selectability Extraction
Using pypdf.PdfReader, text is extracted page-by-page. Scanned image-only files or corrupted pages are programmatically verified and removed to maintain database text SELECTABILITY.
3
Overlapping Chunking Bounds
Text is split into 800-character blocks with a 100-character overlap. This overlap ensures sentences and topics remain semantically connected across chunk splits.
4
Rest-Based Batch Embeddings
Blocks are sent in batches of 50 to OpenRouter's openai/text-embedding-3-small API, producing 1536-dimensional float vector coordinates. ChromaDB Persistent Client indexes these lists directly on disk.

Ingestion & Vector Database Code

# Load Persistent ChromaDB client and retrieve collection
client = chromadb.PersistentClient(path=VECTOR_DB_PATH)
collection = client.get_or_create_collection("fsc_syllabus")

# Batch text slices and send to OpenRouter REST Embeddings API
payload = {
    "model": "openai/text-embedding-3-small",
    "input": batch_chunks
}
response = requests.post(
    "https://openrouter.ai/api/v1/embeddings",
    headers={"Authorization": f"Bearer {api_key}"},
    json=payload
)
embeddings = [item["embedding"] for item in response.json()["data"]]

# Store vectors, metadata, and plain text in ChromaDB persistent collection
collection.add(
    ids=batch_ids,
    documents=batch_chunks,
    embeddings=embeddings,
    metadatas=batch_metadatas
)
Optimization for Low-Resource Environments

We switched from heavy local transformer libraries (e.g. SentenceTransformers / PyTorch) to REST-based OpenRouter embeddings. This reduced memory footprints, eliminated 200MB+ weight downloads, and kept the Python backend fast and lightweight.

3Live Exam API Server (`app.py`)

The Flask backend handles question requests through /api/generate-rag-exam. It retrieves relevant semantic vectors and instructs the LLM to write structured mock exam questions.

1
Semantic Query Embedding
The API embeds the search query (subject name, e.g. "Physics") using the OpenRouter embeddings API to generate a search coordinate list.
2
Vector Database Semantic Search
The database matches query coordinates against text blocks. ChromaDB returns the **top 25 context blocks** using cosine similarity.
3
Few-Shot Style Template Mapping
The server pulls a random solved past-paper question from a local past_papers.json file. This template teaches the AI to follow the exact question format, option layout, and style of Pakistan boards.
4
Batch Split & Llama 3.3 Inference
To prevent LLM rate limits and token truncation, the count is split into batches of max 15. The prompt specifies a balanced difficulty layout (30% Easy, 50% Moderate, 20% Hard) and requires a raw JSON array response.

# Inference call with fallback to offline database

Dual-Layered Resiliency Loop

If the internet drops, an API rate limit is hit, or the AI outputs invalid JSON syntax, backend exception handlers catch the error and serve pre-written, solved past paper questions instantly. The student's testing session is completely protected from database crashes.

4Mock Exam Engine & Client Logic

The client React application (MockExam.jsx & EntryTestPrep.jsx) coordinates exam sessions, timing, score metrics, and anti-cheat tracking.

Official Pakistan Entry Test Blueprints

The client loads official exam blueprint configurations:

  • Medical Pattern (MDCAT): 180 questions (Bio 81, Chem 45, Phys 36, Eng 18) | 180 Mins | No negative marking (+1 correct, 0 incorrect/unattempted).
  • Engineering Pattern (ECAT): 100 questions (Math 30, Phys 30, Chem 30, Eng 10) | 100 Mins | Negative marking (+4 correct, -1 incorrect, 0 unattempted).

Dynamic Mock Exam Run-Time & Anti-Cheat

1
Firestore Session Tracking
When a student launches a mock exam, a session record is created in Firestore (test_history) with a status of started. Exiting early updates the status to aborted.
2
Anti-Cheat Tab Visibility Warning
A visibilitychange event listener tracks browser window switches. The student receives warning overlays for the first two switches. On the 3rd switch, the test is auto-submitted.
3
Practice Mode vs Test Mode
Practice tests display answers immediately, highlighting correct options in green, incorrect options in red, and opening an explanation card. Full mock tests hide checks until submission.

// Score calculations matching official Pakistan board blueprints
let correctCount = 0;
let incorrectCount = 0;
let unattemptedCount = 0;

questions.forEach((q, idx) => {
    const userAns = answers[idx];
    if (userAns === undefined || userAns === "") unattemptedCount++;
    else if (userAns === q.answer) correctCount++;
    else incorrectCount++;
});

let score = correctCount;
let maxScore = questions.length;

if (isEcat) {
    // ECAT Negative Marking Formula
    score = (correctCount * 4) - incorrectCount;
    maxScore = questions.length * 4;
}

5Concept Video Companion & Anti-Cheat Logic

The final components of the Entry Test Module are the Concept Video Companion and the client-side safety handlers. These features provide resources for difficult questions and maintain exam integrity.

Concept Video Companion Details

If a student struggles with a concept during a practice test, they can query it directly in the resources dashboard. The system integrates:

  • Keyword Query Enrichment: The dashboard appends academic qualifiers (e.g. "FSc entry test complete tutorial") to standard keywords before passing them to the YouTube search endpoint. This removes irrelevant videos.
  • Bookmark Storage Cache: Bookmarked cards are stored locally in the student's browser. This is done by writing key-value lists to localStorage under edunest_saved_videos. This saves user progress offline.
  • Overlay Iframe Player: YouTube embed links load inside a dark, full-screen React overlay layout. This prevents student distraction by keeping them inside the EduNest app environment.

Anti-Cheat Visibility Implementation

// React Event Hook to prevent window swapping during live tests
useEffect(() => {
    const handleVisibilityChange = () => {
        if (document.hidden && !isFinishedRef.current) {
            setTabSwitchCount(prev => {
                const newCount = prev + 1;
                if (newCount >= 3) {
                    setIsFinished(true);
                    saveResult(true, "Tab Switch Limit Exceeded");
                } else {
                    setShowWarning(true);
                }
                return newCount;
            });
        }
    };
    document.addEventListener('visibilitychange', handleVisibilityChange);
    return () => document.removeEventListener('visibilitychange', handleVisibilityChange);
}, []);
